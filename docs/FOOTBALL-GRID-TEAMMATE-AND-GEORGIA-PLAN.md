## 2. Plan — three phases, each its own release and PR, smallest first

### Phase 0 (this week): relabel + regression fixtures + safe cutover mechanics
Goal: stop the misleading promise without touching data semantics.
1. **Labels.** Change the teammate template to *club* wording in all four locales: en "Club teammate of X", ka "ერთ კლუბში ითამაშა X-სთან", es "Compañero de club de X", tr "X ile aynı kulüpte oynadı". Touch both the generator (`build-launch-manifest.py:763`) and `football-grid-label-locales.ts` (regex at :26 must accept the new prefix; add the es/tr templates). **Scope the locale fixture `build`/`apply` to the new release id** (today `build` reads all releases keyed by `criterion_key` and `apply` rejects a differing English label — old and new releases would collide). Publication must write es/tr labels, not only en/ka.
2. **Regression fixtures** (`tests/football-grid/content-fixtures/`): the reported pairs (Messi × Agüero → *not* a club teammate; Di María × Ligue 1 → yes; Messi × Serie A → no), transfer-boundary cases, a national-team-only pair, and a check that every eligible intersection member of each fixture board is present in `football_grid_board_answers` (runtime resolves against materialised board answers, `repo.ts:2614`, so answer-set completeness is the real guard, not an earliest-date heuristic).
3. **Cutover mechanics** (used by every phase):
   - **Prerequisite for every prod manifest: player identity reconciliation.** Any staging-built manifest may reference staging UUIDs. Before validating a prod manifest: import missing core players with `reference-import.mjs` (natural keys tm/wikidata, prod UUIDs kept); then remap translation foreign keys and import translations with `catalogue-reference-import.mjs` (its identity includes `football_player_id`); then remap every manifest reference — memberships, aliases, `players[].id`, recognizable samples, teammate keys, asset keys — and assert every referenced player exists on prod. `publish` never creates players (`content.ts:459`).
   - Staging: `generate → validate → review → publish → activate --asset-registry` ; play 20 boards as guest + member; two-replica rehearsal.
   - Prod: `publish → activate` the new release **first**, verify `selectBoardIdForUsers` returns its boards; then **quarantine the two old releases** (admin `POST /admin/football-grid/content/quarantines` with `releaseId`, no `boardId` → whole release, `action: disable`, **no `expiresAt`** (expiry re-enables the release unless another disable remains, `repo.ts:1722-1729`), reason `superseded-by-<version>`), and only `retire` them after the window. Cutover disables are **non-expiring**. Semantics per `repo.ts:1722-1729`: a board is excluded while an uncancelled release- or board-level `disable` exists; a later release-level `enable` cancels earlier release-level disables only. Rollback = `enable` the previous release(s), verify `selectBoardIdForUsers` returns their boards, **then `disable` the replacement** — both steps, in that order; no retire, no republish, no unique-version collision. Board-level disables from the 2026-09-04 quarantine (494 rows) stay in force independently.
   - Concurrency: matchmaking holds a Redis lock (`football-grid-matchmaking.service.ts:47,131`) and match creation takes user-row locks (`repo.ts:1787`); there is no shared advisory lock to reuse. Quarantine leaves the release `published`, so an already-selected old board is allowed to proceed (tolerated, documented). Only `retire` can fail the second published check (`repo.ts:1883`) — so `retire` runs only after the rollback window, off-peak, and selection retries once when that check fails. Rehearse concurrent cutover + reconnect + settlement + next-series board on staging.
4. **Label-only release = manifest transform, not regeneration.** The generator has no clone mode: it reloads staging players, rebuilds criteria, regenerates boards and aliases unconditionally (`build-launch-manifest.py:1255-1274`). Phase 0 therefore adds a `transform-labels` step that takes the **pinned manifest of the served release** (v2026090403; the older v2026082610 is consolidated away and its inventory listed in the PR), rewrites only `label_*` and release metadata, and asserts semantic equality of memberships, aliases, boards, answers and recognizable samples against the source manifest before `publish`. Publication still inserts new release-scoped rows (`content.ts:459,541,564`); that is expected.

### Phase 1: real careers for the anchors, and a separate national-team criterion
Goal: "Club teammate of Agüero" includes Atlético and Barcelona teammates; "Argentina teammate of Agüero" exists as its own square.
1. **Identity-safe career enrichment** (replaces the legends shortcut): a new importer that (a) resolves each anchor by Transfermarkt id **and** Wikidata QID, fails on disagreement, never matches by name, preserves UUIDs, and deduplicates input; (b) pulls P54 spells with the source's own precision (day, month or year) and records it; day-precision evidence drives day-level overlap, year-only evidence is expanded to the full year and flagged `coarse` so the 30-day club rule is applied only to day/month-precision pairs; coarse (year-only) pairs require a shared full season and a matching `appearances.csv` slot when the season is ≥ 2012, and are dropped with a listed reason otherwise; unknown starts are rejected; open-ended spells are bounded by the snapshot date; (c) versions and checksums the Wikidata snapshot like `dataset-2026-08-05.sha256`. `upsert-legends.py` stays for the curated legends list only; it must stop marking current players as `legend`.
2. **Both sides of every pair.** Overlap needs the counterpart's history too. Enrich the whole top-recognizable pool (the 120 targets + everyone appearing on a served board), not just the 60 anchors; the build must **replace** window-truncated club evidence rather than `setdefault`-keep it (:558), resolve every club id it meets (today unmapped clubs are skipped silently, :527), and emit an **omissions report** (pairs expected by fixtures but absent) that fails `validate` when non-empty.
3. **Overlap rule.** Club teammate = same club, overlapping dated spells with ≥ 30 days of overlap inside one season (no July–June expansion of year-only data); evidence carries both players' source statements (`wikidata:` locators when Wikidata supplied the spell; `appearances.csv` only when it did).
4. **National-team teammate.** New criterion family `teammate`, subtype `same-national-team-window`, key `teammate-nt:<country>:<anchor uuid>` (distinct from `teammate:<uuid>` — duplicate keys fail validation at `content.ts:145`). Source: dated senior national-team spells from Wikidata + NT appearance rows; citizenship and caps-only evidence excluded; youth/U-21 teams excluded (fixture). Overlap rule: both players have a senior-team spell for the same country overlapping by ≥ 1 calendar year **and** at least one shared NT appearance date range from the dataset where available; precision policy: day/month-precision spells overlap on real dates; year-only spells are treated **conservatively** as 1 July → 30 June of that season and two year-only spells never establish overlap without NT appearance corroboration; spells with an unknown start are rejected from teammate evidence; open-ended spells end at the snapshot date. NT appearance corroboration is mandatory whenever either side is year-only. Fixtures: precision-boundary pairs (one day-precision, one year-only), youth-only pairs, subtype consistency (a pair may be club teammates, NT teammates, both, or neither). Emit only with ≥ 9 members. Label: "Argentina teammate of X" in four locales.
5. **Portraits/assets:** anchor portraits are cached only if the anchor appears among board answers (:1280-1292); cache anchors independently. League memberships stay dataset-only in this phase (flag it in the report).
6. **Calibration:** benchmark bots on the replacement boards before activation with acceptance thresholds (bot win rate per tier within ±10 points of the current release on the same difficulty; human wrong-answer rate on teammate boards ≤ 50 % in the first 3 days); the governor state is keyed by model/config/tier only, so the content release cannot start calibration clean by itself: `FOOTBALL_GRID_BOT_CONFIG_VERSION` is not implemented (governor queries hardcode config 1 at `football-grid-bot-governor.repo.ts:91,122`, bot policies reject other configs at `football-grid-bot.service.ts:68-70`). Two options, decide in the Phase 1 PR: **(a)** implement config version 2 across policy dispatch, match pinning (`bot_config_version` on matches) and governor ingestion, with tests that existing matches keep config 1 — ~1 day of backend work; **(b)** keep config 1 and add an admin operation that resets the governor per-tier EMA/observations at activation (recorded in `football_grid_bot_action_audits`). Recommendation: (b) for Phase 1, (a) before Phase 2; record release + theme in observations and monitor **per release/theme/difficulty**. Phase 2 additionally reviews recognizable samples and familiarity scores for the Georgian audience before boards are approved.

### Phase 2: Erovnuli Liga — pilot first, then content
Goal: Georgian users get Georgian-league squares that are actually answerable.
1. **Coverage pilot (1–2 days, no release):** reverse Wikidata queries per club (players with P54 = club, dated), canonical club QIDs for the 10 Erovnuli clubs, division membership by season, and an actual appearance source. Wikidata P54 proves club membership, not league appearances. Two acceptable outcomes, decided by the pilot: (i) an appearance source is found and validated (Transfermarkt player pages for Erovnuli seasons, or a Georgian FA/league dataset) → the criteria stay `senior-league-appearance`; (ii) none is found → the Erovnuli criteria are emitted as `club:played_for` membership with the label 'Played for Dinamo Tbilisi', never as a league-appearance claim. No-go if neither six clubs × nine members nor feasible nine-cell boards are reached. Output: how many players per club pass the four gates (usable status, numeric Transfermarkt id, first-party portrait, reviewed KA name) — the generator's gate at :265-286. Decide go/no-go on measured completeness (target: 6 clubs × ≥ 9 exposed members).
2. **KA gate:** `football-grid-translate-player-names.ts` is not in this checkout — recover it from the branch that produced the 7,412 ka aliases or rewrite it; add a `reviewed` status check on `football_player_name_translations` (accepted without review today, :283-286); report exclusions per gate.
3. **Assets:** `football-grid-player-cdn.ts` handles portraits only; club crests and the league logo need the frontend launch-asset registries (`clubs.json`, `leagues.json`) plus the CDN mirror, verified on prod URLs.
4. **Themes:** the `georgia` theme already exists in `content.ts:71` but the manifest builder emits no theme (:1142 → boards default European) and matchmaking pairs equal themes regardless of locale. Specify: pack generation emits `georgia` boards; the client offers the theme and defaults Georgian-locale players to it; mixed-locale pairs fall back to `european`; series continue on the same theme. Verify nine-cell feasibility (three answers per cell, two recognizable, nine-player matching) before boards are approved.
5. **Prod promotion of players:** memberships reference `football_players` UUIDs that must exist on prod; `publish` never creates players (`content.ts:459`). Promote new player/translation rows with the September reference importer (natural keys tm/wikidata, prod UUIDs kept), map staging→prod UUIDs in memberships, aliases, answers, teammate keys and asset keys, then validate the prod manifest.
